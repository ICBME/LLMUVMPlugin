# Lean Semantic Proof Backend

This document describes the current opt-in Lean4 proof backend for SemanticSpecIR
and RefModelIR equivalence.

## Trust Model

Lean proves a fixed theorem statement.  The backend does not trust an LLM to
state what must be proved.  Spec2Backend builds a canonical theorem statement
from the checked `ProofObligation`, symbol table, conditions, and artifact
metadata.  An optional LLM may provide only the theorem proof body.

The trusted result is therefore:

```text
Lean accepted the canonical theorem generated by Spec2Backend.
```

It is not:

```text
The LLM declared the implementation correct.
```

The theorem source is not written to tracked files by default.  Reports record
the theorem source hash, canonical theorem hash, proof body hash, obligation id,
artifact hashes, source AST hash, lowering hash, and axiom report.

## Canonical Theorem Flow

The proof pass is disabled by default.  It runs only when callers include
`"proof"` in the selected passes and pass `proof_backend="lean4"`.

For supported semantic obligations, the backend:

1. Builds a `ProofObligation` from `SemanticSpecIR`, `RefModelPlan`, or
   `RefModelIRAdapter` equivalence context.
2. Translates both sides with the fixed Lean expression translator.
3. Emits a canonical theorem header and proposition.
4. Uses either the deterministic built-in tactic profile or an LLM-supplied
   proof body.
5. Runs `lean --stdin --json`.
6. Runs `#print axioms` and rejects unapproved axioms.

The first version proves expression-level denotation equivalence for the
currently supported subset.  It does not yet define a full Lean inductive
semantics for every SemanticSpecIR or RefModelIR node.

## Optional LLM Proof Body Loop

Callers may pass these `proof_options`:

- `llm_backend`: an object implementing the project `LLMBackend` protocol.
- `llm_model`: optional model name passed to the backend.
- `llm_max_attempts`: maximum proof-body attempts per obligation; default `1`.

The LLM request contains the canonical theorem statement and previous Lean
diagnostics.  The required response is strict JSON:

```json
{"proof_body": "simp"}
```

The backend rejects proof bodies containing theorem-statement or trust-boundary
escape tokens, including `theorem`, `def`, `axiom`, `opaque`, `unsafe`, `sorry`,
`admit`, `import`, `set_option`, `#eval`, `#check`, and `#print`.

If Lean rejects the proof body, diagnostics are included in the next attempt.
After all attempts fail, the checker returns a blocking `proof` issue with code
`llm_proof_failed`.

## Supported Boundary

The current Lean backend supports:

- `bool`, `int`, `uint`, fixed-width `bitvector(width)`, and unique-choice
  `enum`.
- Pure `compare`, `unary_op`, `binary_op`, `mux`/`if`, `concat`, `slice`,
  `reduce`, constraints, and implication.
- Semantic proof obligations for `assignment`, `constant_relation`,
  `conditional_assignment`, and the current one-step state-transition subset.

Unsupported expressions or types return blocking proof issues.  Temporal/SVA
and protocol proofs remain outside this backend version.

## Implementation Boundary

`wrapper_template_check` is a static AST template check, not a Lean proof of
Python.  It verifies that the generated wrapper follows the deterministic
`RefModelInterpreter` template.  `RefModelInterpreter` and the Python runtime are
still trusted runtime boundaries.
