# IR-driven BFM Generation Framework

## Goal

The BFM implementation is generated by an agent. The agent reads RTL source,
register descriptions, protocol notes, and design documents, then emits DUT
specific BFM code. This repository provides only the protocol-neutral framework:

- An inspectable IR that records semantic meaning and concrete DUT paths.
- A resolver that maps IR bindings to cocotb DUT handles.
- A runtime context that generated BFMs can use to access resolved signals.

Reference projects are analysis inputs only. Framework code must not encode any
project-specific or protocol-specific behavior.

## Module Layout

`rtlagent_bfm.ir`

- Defines generic IR dataclasses.
- Stores source artifacts used by the agent.
- Stores interface role names without interpreting them.
- Stores semantic signal bindings to real HDL paths.
- Optionally stores register/field layout as generic context.

`rtlagent_bfm.loader`

- Loads IR from JSON or TOML.

`rtlagent_bfm.resolver`

- Resolves IR `hdl_path` values against a cocotb DUT handle or a Python test
  double.
- Reports missing required bindings by semantic name and HDL path.

`rtlagent_bfm.runtime`

- Provides `BfmRuntimeContext` and `GeneratedBfmBase`.
- Offers basic signal access helpers.
- Does not implement reset, read, write, monitor, handshakes, or timing.

## Generation Flow

1. The agent receives a source bundle, for example RTL files, RDL files, test
   requirements, and design documents.
2. The agent extracts semantic roles and writes an IR.
3. The framework validates that interface roles reference declared bindings.
4. The resolver checks that required DUT paths exist.
5. The agent emits BFM logic that uses `BfmRuntimeContext`.
6. Generated code owns all protocol behavior: timing, handshakes, reset
   sequencing, polling, scoreboarding observations, and transaction decoding.

## IR Shape

The IR separates semantic names from real HDL paths. Interface role names are
agent-defined; the framework does not know what they mean.

```json
{
  "design": {
    "top": "example_top"
  },
  "sources": [
    {
      "path": "rtl/example_top.sv",
      "kind": "systemverilog",
      "role": "dut"
    },
    {
      "path": "docs/example_protocol.md",
      "kind": "markdown",
      "role": "design_doc"
    }
  ],
  "interfaces": {
    "control": {
      "protocol": "agent_inferred",
      "clock": "clk",
      "reset": "rst",
      "signals": {
        "request_valid": "req_valid",
        "request_payload": "req_payload",
        "response_ready": "rsp_ready"
      },
      "metadata": {
        "generator_note": "Roles are interpreted by generated code."
      }
    }
  },
  "bindings": {
    "clk": {
      "role": "clock",
      "hdl_path": "clock_i"
    },
    "rst": {
      "role": "reset",
      "hdl_path": "reset_ni",
      "active": "low"
    },
    "req_valid": {
      "role": "control.request_valid",
      "hdl_path": "valid_i",
      "width": 1
    },
    "req_payload": {
      "role": "control.request_payload",
      "hdl_path": "payload_i",
      "width": 16
    },
    "rsp_ready": {
      "role": "control.response_ready",
      "hdl_path": "ready_o",
      "width": 1
    }
  },
  "registers": {
    "CONTROL": {
      "offset": "0x10",
      "fields": {
        "ENABLE": {"lsb": 0, "width": 1, "access": "rw"},
        "MODE": {"lsb": 4, "width": 3, "access": "rw"}
      }
    }
  }
}
```

If the RTL is renamed, generated BFM code can remain stable when it uses the IR
semantic names:

```json
"req_valid": {
  "role": "control.request_valid",
  "hdl_path": "renamed_valid_i",
  "width": 1
}
```

## Runtime Contract

Generated code should use the runtime context for DUT access:

```python
class GeneratedControlBfm(GeneratedBfmBase):
    async def send_control(self, payload):
        self.ctx.drive_value("req_payload", payload)
        self.ctx.drive_value("req_valid", 1)
```

The example above is illustrative only. The framework does not prescribe how
long `req_valid` stays asserted, which clock edge is used, or what response
means. Those rules must come from the agent's analysis of the design.

## Boundary

The framework may grow generic facilities for provenance, validation,
confidence scoring, and source indexing. It should not grow protocol-specific
BFMs. Protocol code belongs in agent-generated artifacts or optional plugins
selected explicitly by the agent.
